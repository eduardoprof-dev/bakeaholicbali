Safe operations

Rules worth remembering

  • “Cancelled” does not automatically mean “refunded.” Check the refund status.
  • Never paste secret API keys into chat, email or screenshots.
  • Do not approve delivery until payment is confirmed and the package is ready.
  • If a webhook fails, fix and replay it—do not ask the customer to pay twice.

Notification Flow

              
Current operational behavior for customer and admin WhatsApp messages.

            

          

          

            

              Order created
              
Customer can receive a pending-payment template if WhatsApp Cloud API and the template are configured.

            

            

              Xendit paid
              
Xendit invoice webhook marks the order paid, sends receipt links, and waits for staff approval before delivery is released.

            

            

              Staff approval
              
Staff prepares and prints the invoice, then approves delivery. Only then does the app create the Biteship courier request.

            

            

              Admin alerts
              
Automated admin WhatsApp alerts use the admin recipient and template from Integrations. Without those, admin watches the orders page and WhatsApp handoff link.

Developer handover

              
The minimum operational knowledge required to maintain the live store safely.

            

          

          

            

              WhatsApp approval
              
Admin can tap Approve or Cancel from WhatsApp. The app waits 60 seconds and sends an Undo button before creating the Biteship delivery or starting the cancellation/refund flow. Text commands still work: APPROVE, CANCEL, or APPROVE BAK-0001 when several orders are waiting.

            

            

              Production architecture
              
Cloudflare protects the public domain and forwards traffic to Railway. Railway runs the Node server. Persistent order and catalog JSON must remain mounted at /app/data.

            

            

              Webhook routes
              
Xendit: /api/xendit/invoice-callback. WhatsApp: /api/whatsapp/webhook. Biteship: /api/biteship/webhook. Treat callback tokens and app secrets as passwords.

            

            

              Developer source map
              
server.js
  payments, Xendit callbacks, WhatsApp webhooks, Biteship requests

cart.js
  checkout, customer details, payment method selection

admin.js
  admin forms, catalog editing, order fallback controls

invoice.js
  printable receipt, shipping document, tracking links

DATA_DIR
  persistent JSON storage, expected Railway mount: /app/data

            

            

              Safe release checklist
              
Work on a branch. Run node --check server.js, node --check admin.js, and node --test server.test.js. Review the diff, merge through GitHub, confirm Railway is healthy, then smoke-test the storefront without creating a payment.

            

            

              Incident playbook
              
Do not ask a customer to pay twice. First record the order number and time, check Admin and the provider dashboard, then inspect Railway logs. Repair the callback cause and replay the webhook when supported.

            

            

              Backups and data
              
Before structural changes, take a Railway volume backup or export the JSON data. Never replace DATA_DIR with ephemeral storage. A successful deployment does not prove that persistent data is safe.

            

            

              Secrets and access
              
Keep production keys only in Railway variables or the protected integrations store. Require MFA for GitHub, Railway, Cloudflare, Meta and Xendit. Rotate a key immediately if it appears in chat, email, logs or screenshots.

            

            

              Daily operations
              
Approve paid orders in WhatsApp only after the package is ready. Use the Orders section for visibility and fallback actions. A cancellation and a refund are separate states—confirm both.
